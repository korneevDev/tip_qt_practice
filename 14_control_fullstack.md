# Занятие 14. Контрольная работа №4. Система регистрации обращений

## Цель

Проверить умение объединять React-интерфейс, асинхронные HTTP-запросы, сервер на Express, реляционную базу PostgreSQL, проверку данных и автоматизированное тестирование в одном веб-приложении.

## Теория

### 1. Повторение архитектуры перед итоговой работой

Для выполнения контрольной используются знания всех предыдущих занятий. В React создаётся интерфейс, `fetch` отправляет HTTP-запросы, Express проверяет значения и обращается к PostgreSQL через модуль `pg`. База отвечает за постоянное хранение. Браузер не должен получать пароль от PostgreSQL и не должен обращаться к ней напрямую.

```text
┌──────────────────────┐  HTTP/JSON   ┌──────────────────────┐   SQL   ┌─────────────────┐
│ React + Vite         │ ───────────> │ Node.js + Express   │ ───────> │ PostgreSQL      │
│ форма, список, поиск │ <─────────── │ API, валидация      │ <─────── │ tickets         │
└──────────────────────┘              └──────────────────────┘         │ categories       │
                                                                     └─────────────────┘
```

**Пример одного полного действия:** пользователь вводит название и категорию, React проверяет длину названия и отправляет `POST /api/tickets`. Express повторно проверяет тело и выполняет `INSERT ... RETURNING`. PostgreSQL создаёт запись и возвращает ID. Express отдаёт ответ `201` с JSON новой записи. React после успешного ответа обновляет список либо повторно запрашивает его с сервера.

Если произошла ошибка на любом этапе, пользователь должен увидеть сообщение. Нельзя без подтверждения сервера считать, что обращение было сохранено.

### 2. Формат данных и контракт API

Все компоненты системы должны использовать согласованные поля. Пример объекта, который сервер возвращает клиенту:

```json
{
  "id": 7,
  "title": "Не работает подключение к сети",
  "categoryId": 3,
  "categoryName": "Сеть",
  "status": "open"
}
```

`categoryId` — внешний ключ, `categoryName` — отображаемое название, `status` принимает только `open` и `closed`. На клиенте используйте названия полей точно в таком же регистре букв, иначе свойства будут равны `undefined`.

| Операция | Пример запроса | Основной ожидаемый ответ |
| --- | --- | --- |
| Загрузить категории | `GET /api/categories` | Массив `{id,name}` |
| Получить обращения | `GET /api/tickets` | `{ "items": [...] }` |
| Создать | `POST /api/tickets` с `title`, `categoryId` | `201` и объект обращения |
| Изменить статус | `PATCH /api/tickets/7` с `{ "status": "closed" }` | `200` и изменённый объект |
| Удалить | `DELETE /api/tickets/7` | `204`, без JSON-тела |
| Проверить сервер | `GET /api/health` | `200` и `{ "status": "ok" }` |

В приложении следует различать два фильтра: `q` — часть названия, `status` — один из допустимых статусов. Пустая строка поиска означает отсутствие фильтра по названию.

### 3. SQL-схема обращений

У приложения две сущности: **категория** и **обращение**. Одной категории может соответствовать много обращений, но каждое обращение относится к одной категории.

```sql
CREATE TABLE categories (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name varchar(40) NOT NULL UNIQUE
);

CREATE TABLE tickets (
  id integer GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  title varchar(100) NOT NULL,
  category_id integer NOT NULL REFERENCES categories(id),
  status varchar(10) NOT NULL DEFAULT 'open',
  CONSTRAINT title_length CHECK (length(btrim(title)) BETWEEN 3 AND 100),
  CONSTRAINT ticket_status CHECK (status IN ('open', 'closed'))
);
```

Это минимальный рабочий пример схемы. В отдельном SQL-файле добавьте три категории. При создании обращения база сама выдаёт ID, и `status` по умолчанию равен `open`. Операции `UPDATE` и `DELETE` обязательно должны содержать условие `WHERE id = $1`.

Для сохранения данных между перезапусками не выполняйте `DROP TABLE` и не очищайте таблицы при старте сервера. Учебную схему применяют перед первым запуском либо в отдельном шаге подготовки.

### 4. Структура серверного приложения

Рекомендуемое разделение файлов:

```text
server/
├── server.js         # создание Express и запуск сервера
├── db.js             # pool PostgreSQL
├── validation.js     # проверки входных значений
├── sql/
│   └── 001_schema.sql
├── test/
│   └── validation.test.js
├── .env.example
└── package.json
```

`server.js` отвечает за маршруты, а `validation.js` не должен импортировать Express или содержать обращения к базе: чистые функции проще тестировать. `db.js` создаёт пул соединений по `process.env.DATABASE_URL`. Входные значения проверяются **до** выполнения SQL.

```javascript
// validation.js — пример отдельной проверки
export function normalizeTicketTitle(value) {
  if (typeof value !== 'string') return null;
  const title = value.trim();
  return title.length >= 3 && title.length <= 100 ? title : null;
}

export function isTicketStatus(value) {
  return value === 'open' || value === 'closed';
}
```

SQL-запрос для получения списка обычно объединяет `tickets` и `categories`, чтобы UI получил название категории без дополнительного поиска на клиенте:

```sql
SELECT t.id, t.title, t.status,
       c.id AS "categoryId", c.name AS "categoryName"
FROM tickets AS t
JOIN categories AS c ON c.id = t.category_id
ORDER BY t.id;
```

### 5. Параметризация и согласованные ответы об ошибках

Клиент не должен решать, можно ли создать запись: это окончательно определяет сервер. Корректные ответы API позволяют интерфейсу вывести понятное сообщение.

```javascript
// Фрагмент маршрута: title проверен заранее
const result = await pool.query(
  `INSERT INTO tickets (title, category_id)
   VALUES ($1, $2)
   RETURNING id, title, category_id AS "categoryId", status`,
  [title, categoryId]
);
res.status(201).json(result.rows[0]);
```

Сервер не должен пересылать клиенту содержимое `DATABASE_URL`, стек исключения или пароль. Для неверного названия и категории возвращайте `400` с объектом `{ "error": "invalid_request" }` либо более конкретным машинно-читаемым кодом, для отсутствующего ID — `404`, для недоступной базы — `503`. Для повторяемости тестов названия полей и форматы ошибок должны оставаться стабильными.

### 6. Подключение React к собственному API

React-приложение запускается на порту Vite, сервер Express — на другом. В режиме разработки настройте прокси Vite, как показано в базовом материале контрольной: запросы на `/api` будут перенаправляться на Express. На клиенте указывайте **относительные** пути, например `fetch('/api/tickets')`. Это избавляет от необходимости помещать конкретный адрес сервера в каждый компонент.

```javascript
// client/src/api.js
export async function requestJson(path, options = {}) {
  const response = await fetch(path, options);
  if (response.status === 204) return null; // Успешное удаление без тела
  const payload = await response.json().catch(() => null);
  if (!response.ok) {
    throw new Error(payload?.error ?? `Ошибка HTTP ${response.status}`);
  }
  return payload;
}
```

Если сервер не работает, `fetch` может выдать сетевую ошибку до получения HTTP-ответа. Такую ошибку нужно ловить в `catch` вызывающего компонента. HTTP `204` нельзя разбирать через `response.json()`, потому что тело ответа пустое.

### 7. Управление формами React

Каждое поле ввода удобно связать с `useState`. После изменения поля новое значение немедленно отражается в состоянии. В обработчике отправки вызовите `preventDefault`, проверьте название и категорию, затем выполните запрос.

```jsx
// Фрагмент тела React-компонента, где подключён useState
const [title, setTitle] = useState('');
const [categoryId, setCategoryId] = useState('1');
const [saving, setSaving] = useState(false);

<input
  value={title}
  onChange={event => setTitle(event.target.value)}
/>
<select
  value={categoryId}
  onChange={event => setCategoryId(event.target.value)}
>
  <option value="1">Оборудование</option>
  <option value="2">Программное обеспечение</option>
  <option value="3">Сеть</option>
</select>
<button type="submit" disabled={saving}>Сохранить</button>
```

Значение `select` — строка, поэтому перед отправкой преобразуйте его в число и проверьте, что категория существует. При выполнении запроса устанавливайте `saving = true`, а в `finally` возвращайте `false`. Ошибка сервера не должна очищать форму до того, как пользователь исправит ввод.

### 8. Состояния интерфейса: загрузка, успех, ошибка

Для каждой сетевой операции различайте как минимум три состояния:

- **Ожидание:** отображается индикатор загрузки или отключается кнопка повторного действия.
- **Успех:** обновляется список и при необходимости очищается форма.
- **Ошибка:** показывается сообщение, а уже загруженные корректные данные остаются доступны.

При добавлении нельзя оптимистично записывать новую задачу в список как окончательно сохранённую, пока сервер не подтвердил её создание, если в приложении нет механизма отката. В этой контрольной достаточно обновлять список только после успешного ответа.

Для поиска и фильтра по статусу удобно формировать URL через `URLSearchParams`:

```javascript
const params = new URLSearchParams();
if (query.trim()) params.set('q', query.trim());
if (status !== 'all') params.set('status', status);
const url = `/api/tickets?${params.toString()}`;
```

`URLSearchParams` выполняет URL-кодирование строки поиска. На сервере каждое значение `req.query` всё равно необходимо проверять.

### 9. Проверка сценариев и диагностические инструменты

В браузере используйте вкладки **Console** и **Network**. Для запросов к серверу отдельно от интерфейса — REST-клиент либо `curl.exe`. В PostgreSQL проверяйте результаты командами `SELECT * FROM tickets ORDER BY id;` и `SELECT * FROM categories ORDER BY id;`. Набор проверок должен включать позитивные и негативные случаи.

Примеры запросов из терминала (Windows PowerShell):

```powershell
curl.exe -i http://127.0.0.1:3000/api/health
curl.exe -i http://127.0.0.1:3000/api/categories
curl.exe -i http://127.0.0.1:3000/api/tickets
```

Для POST удобно создать текстовый файл `ticket.json` с `{"title":"Нет связи","categoryId":3}` и отправить его:

```powershell
curl.exe -i -X POST http://127.0.0.1:3000/api/tickets -H "Content-Type: application/json" --data-binary "@ticket.json"
```

После создания убедитесь, что возвращённый ID появился в PostgreSQL. При повторном запуске сервера данные не должны исчезнуть.

### 10. Автоматизированные тесты и сборка

Модульные тесты пишутся для чистых функций в `validation.js`. Пример:

```javascript
import test from 'node:test';
import assert from 'node:assert/strict';
import { normalizeTicketTitle, isTicketStatus } from '../validation.js';

test('слишком короткое название', () => {
  assert.equal(normalizeTicketTitle('АБ'), null);
});

test('закрытый статус допустим', () => {
  assert.equal(isTicketStatus('closed'), true);
});
```

Команда `node --test` запускает тесты. В финальном проекте должны быть хотя бы четыре модульных и пять HTTP-проверок. Дополнительно выполните `npm run build` в клиентской папке: сборка помогает обнаружить часть ошибок модулей и синтаксиса, которые могли остаться незамеченными.

### 11. Типичные ошибки интеграции

| Проблема | Причина | Решение |
| --- | --- | --- |
| `fetch('/api/tickets')` возвращает 404 | Не настроен прокси либо сервер не запущен | Проверить `vite.config.js` и адрес Express |
| Вместо JSON браузер получил HTML | Ошибочный маршрут или ответ Vite для неизвестного пути | Проверить URL и вкладку Network |
| Категория не отображается | Не совпадает `categoryId`/`category_id` или нет `JOIN` | Согласовать контракт API |
| `status: 'pending'` записался в БД | Нет ограничения или проверки | Использовать `CHECK`, проверку сервера и `400` |
| После ошибки записи исчезает список | Состояние заменено до подтверждения сервера | Обновлять данные только после успеха |
| `DELETE` приводит к ошибке JSON | Для `204` вызван `response.json()` | Обработать пустое тело отдельно |
| После обновления страницы всё исчезает | Сервер использует массив вместо PostgreSQL | Проверить запросы к базе |
| В репозитории появился пароль | В Git добавлен `.env` | Добавить в `.gitignore`; заменить опубликованный секрет |

Рекомендуется сначала добиться корректной работы API отдельно от браузера, затем подключить React. При неисправном интерфейсе это позволит точно определить, находится ошибка на стороне клиента или сервера.

### Дополнительные примеры и пояснения


Клиент-серверное приложение разделяет ответственность. React отвечает за интерфейс и состояние отображения, Express — за маршруты и проверку запросов, PostgreSQL — за постоянное хранение. Пользовательский ввод проверяется в браузере для удобства, но сервер повторно проверяет каждое значение независимо от клиента.

При отправке формы React должен показать состояние выполнения, затем обработать успешный ответ или ошибку. Ошибка сервера не должна автоматически удалять уже полученные записи. Сведения базы данных не передаются в React: браузер общается только с HTTP API.

**Пример 1. Клиентская функция отправки JSON.**

```javascript
export async function createTicket(data) {
  const response = await fetch('/api/tickets', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(data)
  });
  const payload = await response.json().catch(() => null);
  if (!response.ok) {
    throw new Error(payload?.error ?? `Ошибка HTTP ${response.status}`);
  }
  return payload;
}
```

**Пример 2. Параметризованная выборка по статусу.** `status` должен быть предварительно проверен на принадлежность допустимым значениям:

```javascript
const result = await pool.query(
  `SELECT t.id, t.title, t.status,
          c.id AS "categoryId", c.name AS "categoryName"
   FROM tickets t
   JOIN categories c ON c.id = t.category_id
   WHERE ($1::text IS NULL OR t.status = $1)
   ORDER BY t.id`,
  [status ?? null]
);
```

Функции клиентского API должны работать с относительным путём `/api`. При локальной разработке запросы перенаправляются с Vite на Express. Пример фрагмента `vite.config.js`:

```javascript
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  server: {
    proxy: { '/api': 'http://127.0.0.1:3000' }
  }
});
```

Для итоговой проверки необходимо пройти положительные и отрицательные пользовательские сценарии. Автоматизированные тесты фиксируют ожидаемое поведение логики; HTTP-проверки подтверждают маршруты и коды ответа; инструкция запуска позволяет воспроизвести работу приложения на другой машине. В системе Git сохраняют исходники и пример конфигурации, но не реальные пароли и каталоги `node_modules`.

## Подготовка

Использовать установленное окружение Node.js, Vite/React, Express и PostgreSQL. Подготовить два каталога: `client` для React и `server` для API. Для `client` создать проект Vite или использовать учебную заготовку. Для `server` установить `express` и `pg`, добавить `"type": "module"` в `package.json`. База данных — отдельная учебная база `tip_tickets`, схема создаётся из SQL-файла.

Рекомендуемая структура:

```text
practice-14/
```

Предусмотреть две таблицы: `categories` (`id`, `name`) и `tickets` (`id`, `title`, `category_id`, `status`). Категории: `1 — Оборудование`, `2 — Программное обеспечение`, `3 — Сеть`. ## Задание

Разработать веб-приложение «Система регистрации обращений».

| Параметр | Требование |
| --- | --- |
| ID обращения | Уникальное положительное целое число, формируется БД |
| Название | Строка 3–100 символов после `trim()` |
| Категория | ID одной из трёх существующих категорий |
| Статус | `open` или `closed`; при создании `open` |
| Поиск | По подстроке названия без учёта регистра, до 100 символов |
| Фильтрация | Все / открытые / закрытые |
| Хранение | PostgreSQL с внешним ключом и ограничениями |
| Обмен | JSON через собственный Express API |

Реализовать интерфейсы API:

| Метод | Маршрут | Ответ |
| --- | --- | --- |
| GET | `/api/health` | `200`, `{ "status": "ok" }` |
| GET | `/api/categories` | `200`, массив категорий |
| GET | `/api/tickets?q=&status=` | `200`, `{ "items": [...] }` |
| POST | `/api/tickets` | `201`, созданное обращение |
| PATCH | `/api/tickets/:id` | `200`, обращение с новым статусом |
| DELETE | `/api/tickets/:id` | `204`, пустое тело |

1. Разработать SQL-схему с первичными и внешним ключами, ограничениями длины названия и допустимых статусов. Создать три категории и не менее пяти тестовых обращений.
2. Реализовать указанные маршруты Express; проверять каждое поле. Для отсутствующего ID возвращать `404`, для недопустимого значения — `400`, при недоступности БД — `503`. Все пользовательские значения передавать в SQL параметрами.

### Матрица обязательных испытаний

| Сценарий | Условие | Ожидаемый результат |
| --- | --- | --- |
| Загрузка категорий | База доступна | `200`, три категории |
| Создание обращения | Название 3–100, существующая категория | `201`, присвоен ID |
| Слишком короткое название | Строка длиной 2 | `400`, база не изменилась |
| Неизвестная категория | `categoryId: 999` | `400`, запись не создана |
| Недопустимый статус | `pending` | `400`, старый статус сохранён |
| Чтение отсутствующего ID | Несуществующая запись | `404` |
| Удаление | Существующий ID | `204`, пустое тело |
| Повторное удаление | Тот же ID | `404` |
| Поиск без результатов | Несуществующая подстрока | `200`, `items: []` |
| Отключение БД | PostgreSQL недоступен | `503` на маршрутах, требующих БД; UI сообщает об ошибке |
| Перезапуск сервера | Ранее созданные обращения | Данные сохранены |
| Повторная отправка | Быстрые двойные нажатия | Не создаются случайные дубликаты из интерфейса |
